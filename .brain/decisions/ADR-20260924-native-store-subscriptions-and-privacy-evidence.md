# Native software subscriptions and privacy evidence

**Billing-scope supersession, 28 September 2026:** the owner clarified that the mobile app is a per-user paid convenience while the web dashboard is free. Every mobile user, including member and staff/admin roles, purchases their own six-month or annual app-access subscription. The tenant-plan store binding and tenant-entitlement application described in this historical ADR are not the first-release target. Retain reusable provider-verification, notification, retry and privacy safety principles, but do not sell the old tenant-plan products or claim their source implementation fulfills the corrected launch scope. See [the per-user mobile billing ADR](ADR-20260928-per-user-mobile-app-access-subscriptions.md).

Equal-time provider evidence, 28 September: two distinct provider states verified in the same millisecond have no safe ordering. Inside the Serializable entitlement transaction, reject the second state as a retryable conflict with no write; an exact repeated payload at that timestamp is a no-op. A client Restore or provider notification redelivery must re-query current state with a fresh verification time. This favors temporary review over last-writer-wins access changes and still needs signed-store ordering and retry QA.

RTDN unknown-event guard, 28 September: treat any unfamiliar top-level key in Google's decoded `DeveloperNotification` as an unreviewed event shape. Do not strip it and acknowledge a known sibling subscription event; return retryable 503 before Play lookup or entitlement application. Google's published event fields are mutually exclusive. This intentionally requires monitored redelivery and operator/schema review for future event shapes, and it does not prove live Pub/Sub delivery.

Callback review retention, 28 September: a successful purchase callback must not clear a review flag left by an earlier unresolved purchase, timeout, or store error. It can verify and refresh its own entitlement, but another checkout remains blocked until Restore reconciles the store account. A fully applied Restore receipt may clear prior review, subject to the whole-batch unresolved and mixed-account guards. This may require one extra Restore after a delayed success; signed-device callback-order tests must establish the real sequence.

Mixed-account Restore results, 28 September: classify every returned transaction by the current cooperative binding. A batch containing both a matching purchase and an unmatched or unbound purchase still verifies the matching one, but keeps new checkout behind the review gate and directs the operator to the relevant cooperative or billing support. A successful matching receipt cannot erase the unmatched receipt's recovery need. This is a conservative source-level safeguard pending signed StoreKit/Play tests of actual multi-account results.

Restore batch reconciliation, 28 September: verify every matching purchase returned by one Restore query even if an earlier receipt fails. Preserve the purchase-review gate if any receipt fails verification, remains pending, or verifies without an applied entitlement; a later successful receipt cannot clear that earlier unresolved result. This avoids stranding a valid later receipt or exposing another checkout after partial restoration. The server remains the entitlement authority, and signed StoreKit/Play multi-receipt QA is still required.

Purchase-error correlation, 28 September: while a checkout waits for a provider callback, only a purchase error naming its expected product may end that wait and release the UI. An unrelated or unscoped error cannot prove the pending charge failed, so it leaves the watchdog and Restore-first gate active. A direct `requestPurchase` rejection remains recoverable through the existing catch path. This favors avoiding a second charge over immediate retry after an unidentified error; signed-device QA must check whether real cancellation errors carry `productId` or `productIds` and whether the 30-second fallback is usable.

Restore and verification overlap, 28 September: keep the native checkout busy while either a Restore query or a purchase callback's server verification is unresolved. The UI may unlock only after both finish and no purchase callback is pending; this applies to success, error, watchdog and late purchase-request paths. This prevents a second checkout becoming available during an unresolved charge. The local operation gate is tested in both completion orders; signed-device callback timing remains a release gate.

RTDN format follow-up, 28 September: Google's published notification envelope and applicable nested test/subscription/pending-review payloads carry independent `1.0` versions; subscription notices also carry `notificationType`. The authenticated handler now rejects missing/unknown versions and missing type before any Play lookup or entitlement/chargeback receipt, returning 503 for investigation and monitored redelivery. It still re-queries current Play state rather than granting from the type, and it retains unfamiliar positive refund-reason codes for human review as Google advises. This is source contract hardening, not live notification acceptance. Google's `orders.reviewrefund` first call wins despite later OK retries, so any future operator response needs immutable approved intent and exact-request retry rather than a mutable recommendation.

Google acknowledgment follow-up, 28 September: Play acknowledgment is now conditional on the tenant entitlement actually being applied, not merely on provider verification and Play's `ACKNOWLEDGEMENT_STATE_PENDING` flag. The client-verification route keeps `applied: false` recoverable without acknowledging; the RTDN route returns 503 for an unapplied purchase that still requires acknowledgment. This is a money-safety decision: Google defines acknowledgment as notice that the entitlement was granted. A persistent unapplied purchase needs urgent reconciliation within Play's acknowledgment window; this code does not choose an automatic refund or override ownership/chain checks.

Native finalization follow-up, 28 September: installed `expo-iap` 5.6.3 implements Android `finishTransaction` by calling Play acknowledgment. The mobile listener therefore never finalizes Google purchases; the authenticated server verification and RTDN paths own that action after entitlement application. On iOS, the listener finishes only an applied transaction. A verified but unapplied purchase remains in Restore/support review, with signed-device replay and acknowledgment tests required before sales.
The callback event guard's recent-success suppression now records only an applied entitlement. Provider verification with `applied: false` leaves the transaction eligible for immediate re-verification; it does not lift the purchase-review gate or acknowledge Google.

Purchase-error callbacks are ignored while a purchase transaction is still being verified. A late cancellation or generic error must not clear the native busy state before the server result returns, because that would permit a second checkout tap against an unresolved charge. Outside active verification, cancellation keeps its normal recovery behavior; the brief post-success suppression remains limited to transient service errors. This is source-level race protection pending signed-store callback-order QA.

Platform review visibility follow-up, 28 September: the encrypted pending-refund provider event is exposed only through a platform-owner-checked, read-only queue that projects order and deadline metadata. A second database owner check prevents a stale caller context from reading token material. The queue cannot decrypt tokens or submit refund suggestions. A visible queue is not monitored alerting or an approved staffed response path; do not change the retryable HTTP 503 or live-topic gate on the strength of this view.
Delivery-observability follow-up, 28 September: the existing provider-event `attempts` counter starts at one on receipt and increments only after an idempotent duplicate matches private evidence. The restricted queue exposes the count and row update time as tracked push activity, with null for legacy zero-count rows. No new schema or migration is needed. This is local visibility into received pushes, not proof of Pub/Sub retries, dead-letter handling, operator alerting or a submitted chargeback response.

Status: Accepted architecture; launch implementation incomplete.
Date: 24 September 2026

The owner selected Apple/Google subscriptions for mobile software plans. Keep cooperative financial transactions separate from SaaS purchases. Reuse TenantSubscription and provider-event authority; never create a competing client entitlement system. Bind store purchases to the stable tenant subscription UUID, verify current provider state server-side and use serializable ownership/state updates. Store notifications also require verification. Restrict sandbox grants to classified QA tenants. A new native runtime version is required for the purchase module.

Follow-up, 25 September: the legacy plan-request API still retains tenant-scoped checkout-intent history, but any intent tagged `requestState.channel=mobile` must return no hosted checkout URL even if an operator later marks it ready and the URL host is allowlisted. The request's status remains readable; mobile software purchase belongs to Apple/Google native billing. The production-contract Android QA journey now checks the current subscription snapshot, an active QA tenant's configured Google catalog/binding and a visible native offer/price without initiating payment. It blocks when the sandbox catalog is absent. This is offer-discovery evidence only; purchase, restore, renewal, cancellation and refund still require signed-device/store-sandbox proof.

Privacy request evidence is separate from generic support-case closure and financial ledgers. Maintain explicit verification, access revocation, processing and completion states. Preserve shared financial records until retention/erasure scope is reviewed; do not represent account anonymisation as full erasure. Versioned LegalAcceptance snapshots are a foundation for approved published policies, never for current review drafts.

The app-owned iOS privacy manifest now declares ten linked App Functionality categories from the mobile/API data flows. In a disposable production prebuild, CocoaPods aggregated the linked packages' required-reason API declarations into the app manifest, so no duplicate hand-written reason list was added to Expo config. Sentry's Pod manifest separately declares diagnostic categories. This generated-project evidence does not decide actual runtime collection, SDK linkage, tracking, App Store Connect answers or final IPA contents; the exact signed archive and Xcode privacy report remain mandatory evidence.

Consequences: credentials, store catalog/pricing, device evidence and operational privacy/retention decisions remain release gates. Local schema push is not a migration deployment: preexisting migration drift must be reconciled safely. No destructive reset is authorized by this decision.

Google Play product changes use `ReplacementMode.DEFERRED`. A new purchase token can represent the old entitlement plus a queued replacement without an expiry. The server must bind and acknowledge that new token while preserving the old tier until the first renewal; it may select the new tier only when that item is the sole live item. This behavior is covered by policy tests but still needs a Play license-test purchase and renewal before release.

Before Android purchase dispatch, classify available Google purchases for the store account. A sole purchased, unsuspended, same-cooperative, different-product transaction with a token can be the prior subscription in a deferred replacement. An already-owned target product, pending or suspended purchase, queued replacement, missing token, multiple matching purchases, or a purchase bound to another cooperative requires Restore/support review and cannot start another checkout. This prevents a source-level duplicate or conflicting replacement attempt; Play sandbox behavior and the provider's final entitlement still need verification.

Follow-up, 28 September: the prior purchase's product ID must also be present in the active Google catalog before it can be used as a deferred-replacement predecessor. An old, retired or otherwise unrecognized product is routed to Restore/support review. This prevents passing an arbitrary store-owned product as `oldProductId` to Play; migration from a retired plan needs an explicit reviewed catalog and provider path.

The applied provider-event record also stores the verified predecessor token digest. A later suspended old-token notification is ignored only when that event history proves replacement; it cannot overwrite the new token. Current-token suspension and unrelated-token rejection retain their normal behavior. This avoids exposing token lineage in the user-facing subscription snapshot.

Google's RTDN setting for subscriptions also includes voided-purchase notifications. For a voided **subscription** order, the webhook now re-queries the purchase token through the Play Developer API and applies only the verified current entitlement; a voided-order signal alone does not prove that all later paid periods are revoked. It rejects conflicting event kinds and does not treat one-time voids or pending refund-review events as subscription grants. A live refund/chargeback workflow, including handling of unsupported events without Pub/Sub backlog and final entitlement reconciliation, remains a first-release acceptance gate. See [Google's RTDN reference](https://developer.android.com/google/play/billing/rtdn-reference).

Pending refund-review intake follow-up, 28 September: an authenticated Google event now creates an idempotent `SubscriptionProviderEvent` receipt keyed by a digest of the pending-refund token. The token is encrypted with AES-256-GCM under a versioned environment key, while order/reason, token digest, first receipt and a conservative 24-hour deadline from the earlier provider event or receipt time remain in the private event payload. The handler deliberately returns 503 after storage, so no Pub/Sub success claims an unstaffed financial review complete. It neither calls Google's `ReviewRefund` API nor changes entitlement. The keyring must be configured and retained through outstanding reviews; loss of the key makes those tokens unusable. A platform-owner-only review queue, alerting, documented evidence/retention and an approved human response path are still required before a live topic may be enabled. The source-level receipt is not a completed chargeback workflow.

Google SubscriptionsV2 `startTime` is the original grant time, not a reliable current renewal-period start. Persistence now leaves `TenantSubscription.currentPeriodStartsAt` null for Google-verified states instead of mislabeling that date; the verified line-item expiry remains the period end, and the grant time stays in the private provider-event payload for chain ordering. Apple signed transactions retain their actual purchase-date period start. This does not change active/grace/suspended entitlement decisions.

Native purchase callbacks are event-driven. Deduplicate one in-flight transaction and suppress a brief repeat after verified finish; permit immediate **verification** retry after failure and later restore/reconciliation. Suppress a transient StoreKit service error during processing or immediately after verified success so it cannot replace a successful result. This follows the [Expo IAP event/duplicate guidance](https://github.com/hyochan/expo-iap/blob/main/docs/docs/guides/faq.md); it is client presentation/retry safety, while server provider verification remains the entitlement authority.

The native callback must use both fields of the server verification result. It finishes an Apple transaction only after `verified: true` and `applied: true`; it never finishes Google transactions because the server owns acknowledgment. `applied: false` is a verified provider event that did not change the tenant entitlement, so the UI must not claim the plan refreshed and must keep another purchase behind Restore/support review. The server remains authoritative for why an event was not applied.

A purchase action accepts only the exact offer object resolved by the active store connection for the current account scope. The catalog lookup also requires the mapped store to match the device store. A stale rendered offer from a prior cooperative or reconnect cannot dispatch a purchase using the new cooperative's account binding; the user must select a currently loaded offer. Server verification and the tenant binding remain authoritative even when this client guard passes.

Source follow-up, 26 September: new purchase also requires a fresh subscription snapshot with working billing infrastructure, an available mapped plan and a subscription UUID. The hook compares that reviewed UUID with the active catalog account binding again at dispatch. A fail-safe snapshot or a catalog refreshed for another cooperative cannot start a new charge, while Restore and Manage remain available. This is a client-side guard; signed-device store and server-entitlement evidence remain required.

The installed `expo-iap` 5.6.3 implementation says `requestPurchase` returns a dispatch result, not the purchase outcome. If it returns without a matching purchase/error listener callback, the native screen waits 30 seconds, then opens Restore/Manage while disabling another purchase and showing restore-first guidance. A callback for a different product cannot cancel that wait. Scope disposal cancels the timer; a matching verified callback clears its watchdog but preserves any existing purchase-review gate, while a Restore that finds no purchases can clear that gate. This is a UI recovery path, not proof that the store did or did not charge; signed-store tests must exercise callback, no-callback, delayed-callback and restore outcomes.

Publisher qualification is a separate gate from the native billing architecture. The owner's individual iOS-team preference is recorded, but Apple's current legal-entity guidance for regulated financial services or sensitive-data apps requires classification review before any public individual-team submission. Google's financial-service publisher requirements similarly block use of the observed Personal Play account without an eligible Organization route. See the store-listing review runbook; this ADR does not approve either current personal account for public launch.
