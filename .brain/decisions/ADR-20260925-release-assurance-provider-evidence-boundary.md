# ADR: Release Assurance Uses Pinned Logic And Trusted Provider Evidence

- Status: Accepted
- Date: 2026-09-25

## Context

One Halalvest revision can require a Prisma push, Dashboard and Marketing web
deployments, an Expo build or update, and a Trigger.dev deployment. Applying
only part of that graph can expose incompatible financial or authorization
behavior. A successful command or historical deployment is not proof that the
intended revision is currently active.

## Decision

- Pin the shared `local-infra-kit` release toolkit by full Git revision and
  checksum inventory under `.release/toolkit/`.
- Keep Halalvest topology in `release.manifest.json` and a thin provider adapter;
  shared planning and verification logic stays in the toolkit.
- Keep local `release:plan` and `release:status` advisory. A missing baseline
  must report every target instead of claiming green.
- Let only protected CI decide release readiness using fresh provider evidence
  bound to Halalvest, the selected environment, and the exact commit.
- Accept normalized provider facts only in a short-lived HMAC-signed bundle
  generated by a trusted authenticated collector. Hand-authored repository JSON
  is not release evidence.
- Reconcile historical receipts with current database, Vercel alias, Expo
  channel/build, and Trigger worker state.
- Keep Preview and Production independent. An unsupported Trigger Preview path
  requires a protected, commit-scoped, expiring waiver; Production is never a
  Preview fallback.
- Keep this workflow verification-only. Later deployment automation must remain
  downstream of the same plan and gates.

## Consequences

The source integration can be reviewed without touching financial data or
providers. Hosted activation remains fail-closed until the isolated Preview
database/API, collector, protected environments, and provider controls are
configured and accepted.
