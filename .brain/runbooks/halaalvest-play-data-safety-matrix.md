# Google Play Data safety evidence matrix

Draft for source review, 24 September 2026. No Play Console answers have been submitted. This covers the proposed production Android package `com.halaalvest.mobile` and the backend/SDK transfers triggered by it. Final answers must be checked against the signed binary, enabled environment variables, production processors and published privacy policy.

Google defines **collected** as transmitted off-device, including through SDKs. **Shared** can include server-to-third-party transfers, while a provider acting only on the developer's instructions can qualify for the service-provider exception. Pseudonymous identifiers still count. “Optional” requires every user to be able to avoid the collection; a feature used only by some roles is not automatically optional. Google Play Billing card details need not be declared if HalaalVest never accesses them and the store collects them directly. [Official Data safety guide](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en); [account-deletion rules](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).

## Cross-cutting release answers

- **Encrypted in transit:** release mobile API/dashboard URL policy requires HTTPS, and the identified Logly, Expo push and Resend endpoints use HTTPS. This is source evidence only. Do not answer “all data encrypted in transit” until a signed production Android network/SDK audit covers every destination, redirect and upload path. `apps/mobile/src/lib/mobile-service-url.ts`, `apps/mobile/src/lib/mobile-trpc-client.ts`, `packages/notifications/src/mobile-push.ts`.
- **Deletion:** in-app account-privacy request and external email-verified request entry exist. Verified platform owners can revoke account access locally after handover review, but eligible erasure, restricted retention, backup/processor deletion and completion notice are unfinished. The public deletion URL is still draft/unpublished. Do not claim completed account/data deletion on this evidence. `apps/mobile/src/features/account-privacy/`, `.brain/features/launch-legal-and-store-readiness.md`.
- **SDK and web content:** inventory `expo-iap`, Expo notifications, Sentry and Logly on the final binary; inspect merged Android manifest and network traffic. Legal links use the system browser (`Linking.openURL`), not an app-controlled WebView. Review every app-controlled web surface if one is added. `apps/mobile/src/components/app/legal-links.tsx`.
- **Android storage/media and overlay permissions:** the old signed versionCode 12 validation AAB declared `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `READ_MEDIA_IMAGES` and `SYSTEM_ALERT_WINDOW`. Source review found report export using only `expo-file-system`'s app-private cache and the OS share sheet, with no shared-media picker or draw-over-other-apps flow. Expo's base Android template supplies the overlay permission. `apps/mobile/app.config.ts` blocks all four for distributable builds, retaining the overlay permission in development builds for React Native debugging. The signed [versionCode 14 cloud native-validation AAB](https://expo.dev/accounts/cipron-startups/projects/halaalvest/builds/3823cfe4-d0e6-40d9-8782-24e01cc23c07) and the later versionCode 16 and 18 **local** validation AABs omit all four; Billing remains present. The current-source v18 result was checked with bundletool from the signed AAB (SHA-256 `15ef8c9c9a88a88265933c0b0cc82547bbcf88050a3e142f60a1f07e999d52ad`). This proves the merged permission result for those exact builds, not device report-export behavior, final release-binary declarations or the data-type/processor questions above. [Expo permission configuration](https://docs.expo.dev/guides/permissions/); [Android app-specific storage](https://developer.android.com/training/data-storage/app-specific); [Android overlay permission](https://developer.android.com/reference/android/Manifest.permission#SYSTEM_ALERT_WINDOW).
- **Screenshot detection versus capture protection:** the v16 merged manifest includes install-time `DETECT_SCREEN_CAPTURE` for Android 14+ from `expo-screen-capture`. App code calls `preventScreenCaptureAsync` for app-lock privacy, which uses Android `FLAG_SECURE`; no application screenshot-listener call was found. The installed Expo 8.0.10 native module nevertheless registers Android's screenshot callback when created, so removing its manifest permission without changing that native initialization could break startup. [Android's detection API](https://developer.android.com/about/versions/14/features/screenshot-detection) reports a screenshot event without image pixels and shows a system notice to the user. This permission alone does not prove HalaalVest collects screenshot contents off-device; inspect actual v16/final runtime behavior and SDK traffic before a Play data-type answer, and review whether the automatic callback is necessary for release.
- **Server-to-third-party:** verify Resend email, Expo push, Logly collector, Sentry, hosting/database and Trigger jobs, plus any payment, document storage, KYC or banking provider actually enabled for launch. A server transfer can be Sharing even if no mobile SDK calls that provider directly. Classification as a service provider requires terms and processing purpose evidence.
- **Store billing:** Apple/Google verification and notifications exchange purchase IDs/tokens/account binding. Raw Google purchase tokens are not persisted by the HalaalVest server; a digest and provider event evidence are. Confirm production products and capture the actual payloads before final form choices.
