# ADR — Align Expo native and Metro module resolution

Date: 24 September 2026
Status: Accepted for local preflight; signed-build verification pending.

## Context

Expo Doctor found SDK 54 patch mismatches and duplicate native-module installations in the Bun workspace. Some duplicates are the same version materialised under different isolated peer contexts; `expo-constants` also appears at 18.0.13 under transitive packages while the mobile app resolves 18.0.14. The wider monorepo intentionally has React 19.2.7 for web/email and React 19.1.0 for Expo. A broad reinstall or linker change would affect all apps and cannot itself prove which module the signed native build links.

## Decision

Align the mobile manifest and lockfile to Expo Doctor's current SDK 54 patch set: Expo 54.0.37, `expo-constants` 18.0.14 and `expo-updates` 29.0.20. Enable Expo SDK 54's `experiments.autolinkingModuleResolution` so Metro follows the native autolinking choice when isolated installs contain multiple copies. Preserve the monorepo's existing Bun linker and web React versions pending a bounded build investigation.

## Consequences

Expo Doctor's version check now passes, as do mobile TypeScript and the full source contract. Its duplicate-dependency check still fails (17/18 checks pass). A local `expo-modules-autolinking verify --platform ios --json` exits successfully and selects one `expo-iap@5.6.3`, but reports four native-module duplicate groups: `expo-constants` (selected 18.0.14, with 18.0.14 and 18.0.13 copies), `expo-file-system` (19.0.24), `expo-font` (14.0.12), and `react-native` (0.81.5). The resolution flag is a documented mitigation, not deduplication or signed-build proof. Inspect the EAS archive, compile a signed release candidate, and verify runtime startup/IAP before treating the dependency graph as ready. Do not silence the Doctor check or claim a clean native build from config introspection.

A later local iOS verifier run reported six duplicate-installation groups, adding `expo` and `expo-linking` to the earlier four; these are same-version peer-context copies. `expo-constants` remains the only group with both 18.0.13 and 18.0.14. This run does not replace signed archive and runtime evidence.

## Xcode 27 disposable iOS prebuild and pod floor — 24 September 2026

An unsigned `store-qa` iOS probe was generated outside the repository with placeholder HTTPS origins. Expo prebuild succeeded with the release bundle ID and push entitlement; CocoaPods resolved 120 pods, including `openiap`. Xcode 27 then rejected several pods' declared simulator deployment targets below its supported iOS 15 floor, despite the app and generated Podfile using 15.1. A command-line `IPHONEOS_DEPLOYMENT_TARGET=15.1` override passed that failure and compiled native targets, but the copied probe subsequently failed its Metro bundle because its symlinked Bun virtual-store dependencies live outside the disposable workspace. The real workspace's iOS Expo export succeeds, so that Metro error is not yet evidence of a packaged EAS failure. No signed or complete native build is established.

Keep the pod floor correction in managed prebuild through the local `with-ios-pod-deployment-target` config plugin. It appends an idempotent `post_install` adjustment that raises numeric pod deployment targets below the app's configured iOS minimum, without lowering higher targets. Repeated disposable Expo prebuilds produced one adjustment, `ruby -c` passed, and a fresh CocoaPods install generated 276 deployment settings, all at 15.1. A second unsigned simulator Release build **without** the command-line target override no longer reported the deployment-target error; it stopped in Metro on `react-native-safe-area-context` resolution from the symlinked temporary dependency tree. The actual repository's iOS Expo export produced a 9.88 MB Hermes bundle. Mobile TypeScript and the full mobile contract pass. A completed native compile from an archive with real in-workspace dependencies, signed store build and device IAP tests remain required; do not count the symlinked probe as those proofs.

A subsequent disposable workspace copied the Bun dependency tree with copy-on-write files while retaining its internal package links; Expo Router, safe-area context, Expo and IAP then resolved inside that workspace. With the same placeholder HTTPS origins and managed plugin, `expo prebuild --platform ios --no-install`, CocoaPods install (120 pods), and `expo export --platform ios` exited 0. From its generated `apps/mobile/ios`, `xcodebuild -quiet -workspace Halaalvest.xcworkspace -scheme Halaalvest -configuration Release -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' -derivedDataPath /private/tmp/halaalvest-ios-real-deps-derived-20260924 CODE_SIGNING_ALLOWED=NO build` exited 0. The built `Build/Products/Release-iphonesimulator/Halaalvest.app` reports `CFBundleIdentifier=com.halaalvest.mobile`, version `0.2.0`, and includes `main.jsbundle`. The disposable workspace and derived data were removed after verification. This resolves the earlier temporary-symlink Metro ambiguity and proves local unsigned simulator compilation of the current source and native modules. It does **not** prove a signed device/store artifact, correct real endpoint configuration, EAS cloud environment, StoreKit purchase/restore, or TestFlight processing.

## Android native linking probe — 24 September 2026

A separate copy-on-write workspace with dependencies inside it passed production-identity Android prebuild. The generated app has `com.halaalvest.mobile`, version `0.2.0`, Play Billing permission and the OpenIAP Android dependency. With placeholder HTTPS origins, `./gradlew :app:assembleRelease --no-daemon` exited 1 twice, including after clearing the copied Reanimated/Worklets build and `.cxx` directories and running `./gradlew clean`. Reanimated 4.1.7's `CMakeLists.txt` imports Worklets 0.5.1's `libworklets.so` from `android/build/intermediates/cmake/release/obj/<ABI>`, while Gradle built the library under `android/build/intermediates/cxx/RelWithDebInfo/<hash>/obj/<ABI>`. The autolinked Worklets root and Reanimated's resolved root pointed to the same Bun virtual-store installation; this was not a duplicate-copy mismatch.

As diagnosis only, symlinks were added inside that disposable Worklets build output from each legacy ABI path to its already-built CXX `.so`. The same Gradle command then exited 0 (`BUILD SUCCESSFUL in 5m 8s`) and produced `app-release.apk` with package `com.halaalvest.mobile`, version `0.2.0`, target SDK 36 and Play Billing permission. `apksigner` identified its certificate as **Android Debug**. The links were never added to source or the upload archive. This proves that the path mismatch is the observed local compilation blocker, but it does not prove a clean EAS cloud build or a Play-ready signed artifact. Reanimated's official compatibility table permits Expo SDK 54 with Reanimated 4.1.x and Worklets 0.5.1; [an upstream Expo issue](https://github.com/expo/expo/issues/40525) reports a similar missing-library path on a macOS SDK 54 build without establishing a general fix. Do not add an unvalidated vendor patch or call the diagnostic APK release-ready; rerun a clean cloud build with approved real HTTPS endpoints and resolve any repeated failure against its exact logs.

## Clean EAS Android result and version deduplication — 25 September 2026

A single clean EAS `store-qa` Android probe with validation-only `.invalid` HTTPS origins finished successfully as [build `8f5f5cfc-196f-46f2-ade3-fe4d66491c9a`](https://expo.dev/accounts/cipron-startups/projects/halaalvest/builds/8f5f5cfc-196f-46f2-ade3-fe4d66491c9a). The remote worker ran `:app:bundleRelease` without the local diagnostic symlinks; Reanimated CMake build and Worklets completed for arm64-v8a, armeabi-v7a, x86 and x86_64. The local macOS path failure did not reproduce on that EAS image. Keep the source free of a Worklets path patch unless a later clean build supplies contrary evidence. The AAB is signed and contains the production package and Play Billing permission, but its endpoints are placeholders, so it is not a usable store candidate.

The cloud install reported a real `expo-constants` version split. Bun reads overrides only from the monorepo root, so the root manifest now pins `expo-constants` 18.0.14 and the lockfile has a single version. A clean hoisted install removes this native version mismatch. Expo Doctor still reports React 19.1.0 inside the SDK 54 mobile app and 19.2.7 in web/email workspaces; applying a global React override would force one app across an unverified compatibility boundary. The local isolated Bun 1.3 layout also shows same-version peer-context copies, whereas the successful EAS Bun 1.2.20 hoisted install did not report those groups. Do not equate Doctor's monorepo warning with a demonstrated duplicate React runtime in the mobile bundle. The post-build dependency change requires a new cloud build before release acceptance.

The post-lockfile Android `store-qa` cloud probe [build `7c0237a4-f208-4dae-839b-599a75beb350`](https://expo.dev/accounts/cipron-startups/projects/halaalvest/builds/7c0237a4-f208-4dae-839b-599a75beb350) completed `:app:bundleRelease` from the revised source without native-linker workaround. Its validation-only AAB is signed but points at `.invalid` endpoints; this closes the current-source cloud compilation question, not production runtime, native purchase or Play submission acceptance. Static 16 KB packaging and 64-bit ELF alignment pass; 16 KB device runtime remains open. See the store-qa identity ADR for artifact hash and checks.
