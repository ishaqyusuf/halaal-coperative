## Context

The `preview` mobile variant uses `com.halaalvest.mobile.preview`, while the Apple and Google verification clients and candidate products use `com.halaalvest.mobile`. A signed preview build can test app flows, but cannot prove purchases for the release app's store products. Apple TestFlight requires a store-distribution build; Google Play license testing requires the package name configured in Play Console. See [Expo TestFlight](https://docs.expo.dev/submit/testflight/) and [Google Play Billing testing](https://developer.android.com/google/play/billing/test).

## Decision

Add an EAS `store-qa` build profile with store distribution, the production mobile app identity, the **preview EAS environment**, and a separate `store-qa` update channel. Expo otherwise defaults a store-distribution profile to the production EAS environment ([Expo environment-variable rules](https://docs.expo.dev/eas/environment-variables/usage/)). The scoped build runner loads `.env.preview` for isolated backend origins, then forces the production app variant so QA-only client capabilities stay disabled. The existing release URL guard rejects the current localhost preview URLs. Keep the ordinary `preview` identity for non-store workflow QA.

The runner requires both release URL variables to be explicitly present in preview-specific env files and overwrites values inherited from the shell or base `.env`. Expo config rejects a `store-qa` build whose app variant is not `production`. These checks prevent accidental fallback to a production URL or the wrong store app identity when preview settings are incomplete; they do not prove that the configured HTTPS service is isolated.

The live EAS Preview environment later showed both API and dashboard URLs set to the known Production host `app.halaalvest.com`. The shared release-environment validator now rejects `app.halaalvest.com` and `api.halaalvest.com` for either `store-qa` service URL, including URLs with a path. Production builds remain allowed to use those hosts; native validation remains explicitly unreachable. This stops the observed cross-environment configuration from silently entering a store-QA app when the legal origin is eventually filled in. It cannot prove that any other HTTPS host has an isolated database, safe QA email routing or reachable service; those require target-specific review and device QA.

The root EAS runner now validates every forwarded option before env loading or authentication. Builds allow only `--non-interactive`, `--no-wait`, `--local` and `--clear-cache`; submissions allow one exact `--id` plus `--non-interactive`/`--no-wait`; updates allow the mobile helper's `--dry-run`, `--skip-publish`, `--current` and `--date`. Duplicate, valueless and unknown options fail. In particular, a build cannot append `--auto-submit` or a second `--profile` to bypass the separately inspected exact-build submission path. The scoped target/platform/account selectors and Android validation-endpoint option retain their existing checks. This is CLI dispatch safety, not proof of EAS service behavior or an approved build.

The production app variant now requires a public legal origin even when no EAS profile variable is present; only the explicit `native-validation` profile exempts this for unreachable-endpoint signing probes. The scoped submission runner performs a read-only `eas build:view <id> --json` after isolated authentication and before `eas submit`. It requires the selected build to match the exact requested ID, project, platform, finished status, store distribution, profile and channel. This rejects a `native-validation` build ID passed with `--store-qa`. The metadata check does not inspect the binary's embedded endpoints, signing chain or store-console eligibility; inspect the exact candidate artifact separately.

For Android AAB review, `scripts/mobile-artifact-origins.ts` reads the `base/assets/index.android.bundle` and `base/assets/app.config` entries without modifying the artifact. It requires exact supplied public HTTPS API, dashboard and legal origins to appear, rejects observed `.invalid` origins, and checks release app name, package, variant, Expo project and update URL. The local v20 native-validation AAB fails as intended: both `.invalid` service origins appear, all three candidate origins are absent, and its app name predates the `HalaalVest` capitalization fix. This is a static byte/config inventory, not proof of runtime routing, absence of constructed/encoded endpoints, package signing or store eligibility. The exact future candidate still needs this check plus normal signed-artifact and device verification before submission. An earlier iOS Hermes export did not expose validation hosts contiguously despite the no-bytecode export containing them, so copying this literal-byte scan to an IPA would be unsound; signed IPA and device-network evidence remain open.

The Android `eas:submit` path now downloads the artifact URL from the exact EAS build metadata into the runner's isolated temporary directory and runs this same origin/identity check before invoking `eas submit`; it prints the inspected AAB SHA-256 and removes the temporary copy afterward. It handles up to five redirects manually and checks each destination for public HTTPS before requesting it. An unavailable metadata lookup, missing artifact, failed download, unsafe redirect, oversized response or failed inspection blocks submission. This is source-tested and exercised with a synthetic AAB; a live EAS candidate and signed-device acceptance are still required. iOS remains on the metadata guard only pending a suitable IPA/runtime verification method.

Release config also rejects reserved placeholder API/dashboard hosts (`.invalid`, `.test`, `.example` and `example.com/.net/.org`) in Preview, store-QA and Production variants. Only the explicitly named `native-validation` EAS profile may embed them for source/native signing probes. This prevents an offline validation endpoint from passing the release config check; it does not prove a non-placeholder host is reachable or isolated, and an exact submitted build still needs artifact-level endpoint verification.

## Native-only validation profile — 25 September 2026

The signed Android versionCode 12 native probe predates later permission cleanup. When preparing a replacement, the EAS Preview environment was found to define both public origins as `https://app.halaalvest.com`; a locally supplied `.invalid` URL does not control those cloud variables. The queued versionCode 13 job was canceled before completion because that origin's isolation from Production is unproven. For source/native manifest probes, `--validation-endpoints` is now accepted only by the scoped store-QA **Android build** runner and selects a separate `native-validation` profile. The runner accepts only `--non-interactive`, `--no-wait` and `--local` as additional options on this path, preventing a profile override or automatic submission. It inherits the release package/store distribution from `store-qa`, pins both URLs to unreachable `.invalid` origins in build-profile `env`, uses its own update channel and disables foreground update checks. EAS logged that the profile values override the Preview environment when queuing versionCode 14. [Expo's build-profile variables](https://docs.expo.dev/build/eas-json/#environment-variables) are set both locally and on the builder; [Expo's precedence reference](https://docs.expo.dev/eas/workflows/environment/#precedence) places profile `env` above remote environment variables. Inspect the finished bundle to prove the exact origins; this profile is never a device/API, store-transaction or submission candidate.

The versionCode 14 native-validation AAB finished and its actual bundle contains one copy of each `.invalid` hostname and no `app.halaalvest.com` string across all entries. Its signed merged manifest omits the four targeted storage/media/overlay permissions while retaining Play Billing. See the exact hashes and packaging checks in [`../tasks/2026-09-24-launch-readiness.md`](../tasks/2026-09-24-launch-readiness.md). This proves the profile's effective bundle values for that build; the ordinary `store-qa` profile remains gated on a verified isolated HTTPS backend and must be built and inspected separately.

When the Expo cloud Android monthly quota blocked the next validation build, the same profile was run through [EAS local builds](https://docs.expo.dev/build-reference/local-builds/). Its initial macOS native compile failed because Reanimated looked for a Worklets library under a CMake path while Worklets had generated it under the CXX intermediates path. Linking those already-built libraries only inside the disposable `/private/tmp` local build tree allowed `:app:bundleRelease` to finish; no repository dependency or native source was patched. The resulting v16 AAB uses the same managed signing certificate as cloud v14, has `.invalid` origins and passed a derived-APK startup and status-bar check on a 16 KiB Android emulator. A local-build workaround is evidence for this exact artifact only; the final store-QA build must use a verified isolated backend and pass its own clean build and signed-device checks.

## Consequences

This profile prepares a correctly identified Android App Bundle or iOS TestFlight candidate once an isolated HTTPS backend, store products, signing credentials and eligible publisher/team exist. The backend must use sandbox verification and QA-classified tenants for test purchases; it must not point at Production or reuse Production financial data. The profile is configuration only: no archive, signing, upload, store transaction, or TestFlight/Play review has been verified. Do not submit under an ineligible individual/Personal publisher while the financial-app classification gate remains open.

## Archive hygiene before a cloud build — 24 September 2026

A local `eas build:inspect --stage archive` revealed that the VCS-backed shallow archive included `.git` and ignored local database backups. The root `.easignore` now excludes `.local`, local tool/report folders and root-only planning files in addition to dotenv, generated native trees and dependencies. This is archive-content evidence only; EAS installation, prebuild, signing and runtime behavior remain unverified.

## Isolated CLI authentication — 24 September 2026

The scoped runner no longer reads or overwrites the shared `~/.expo/state.json` when selecting its EAS account. It obtains a session from the configured account credentials, writes it with owner-only permissions under a temporary home, passes that home only to the EAS child process, and removes it after the command exits, including nonzero exits. This keeps the user's existing Expo CLI identity intact while preserving the selected account for the build, submission or update. A mocked EAS command verified that the child received the isolated session, a nonzero exit was preserved, the temporary home was removed and the shared state hash did not change. Real EAS authentication and cloud-side permissions remain unverified; interruption or process termination before cleanup may leave a private temporary directory for host cleanup.

Gradle `:app:bundleRelease` succeeded with Reanimated CMake builds for all four ABIs. The downloaded signed AAB is 85,862,687 bytes and has SHA-256 `135e87c839210d28165fe306de5e8e93075da66203a41e2714600a0c9c6f3f52`; ZIP integrity and normal JAR signature verification pass. Strict JAR verification reports the expected self-signed/no-timestamp upload-certificate warnings, so this is cryptographic integrity evidence, not a trusted public certificate chain.

Direct ELF program-header inspection found all 27 arm64-v8a and all 27 x86_64 libraries have minimum `PT_LOAD` alignment of 16,384 bytes; 32-bit slices include 4 KB alignments. The AAB was **not submitted to Play** and cannot be used as a release candidate because its API/dashboard origins are intentionally unreachable and store billing, policy and publisher gates remain open.

EAS also warned that `ios.infoPlist.ITSAppUsesNonExemptEncryption` is absent. [Apple defines `NO` as a declaration covering the app and linked libraries](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption), not merely a build convenience. Current mobile source uses standard HTTPS, OS secure storage and hashing/random ID APIs; a final inventory of linked SDK cryptography and the owner's export-compliance answer is still required before setting this Boolean or answering App Store Connect. The missing key did not cause the credential failure, and no value was guessed in source.

The interactive `eas credentials:configure-build --platform ios --profile store-qa` route was also tried with an isolated Expo session. EAS offered Apple login and then required an Apple ID; the command was stopped at that prompt without entering an unknown account or requesting 2FA. The host has no valid code-signing identity for this app, and unrelated GND Millwork signing files were not used. An authorized Zeroes Apple account login/2FA or an approved API-key/manual credential handoff is required; the local Expo session was left unchanged.
