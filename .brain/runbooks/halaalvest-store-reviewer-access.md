## Personal app access review procedure

1. After the per-user entitlement, pre-entry paywall and isolated Production backend exist, create reusable synthetic reviewer users with stable login credentials. One account may cover both member and administrator roles only if actual role switching keeps the same user ID; otherwise provide separate accounts. Keep all data fictional and external finance/messaging side effects disabled.
2. Use the platform-owner-only `mobileAppAccess.issueReviewGrant` mutation for the synthetic feature-inspection user after the isolated Production backend and reviewer account are approved. It requires that user's UUID, a 20–500 character purpose and an expiry more than one hour but no more than 30 days ahead; the server binds the current store environment. The database refuses a live/purging QA tenant, platform owner, self-grant or membership in another tenant, and records an audit event. Renew before expiry; `mobileAppAccess.revokeReviewGrant` ends access with a second audit event. It never changes `TenantSubscription` or cooperative permissions. Verify persistence across session renewal, backend restart and repeat review without a store purchase. Provide a separate unpaid synthetic account to inspect the six-month/yearly paywall and Restore/Manage entry without requiring a real charge.
3. On the final signed build, test both accounts from a clean install and external network. The unpaid account must be blocked from normal feature routes but able to see purchase, Restore, support, deletion and legal options. The review-granted account must enter member and staff/admin feature areas only within its actual roles. Web dashboard access must remain independent of either mobile entitlement. Test session renewal and next-day repeat access.
4. Enter only verified credentials and exact English navigation in the store review forms. Keep them reusable and valid while the app is listed; rotate console credentials before disabling old ones. Do not paste secrets into Git, Brain, screenshots or ordinary support messages.

## Source audit

- Production mobile sign-in accepts a cooperative access code and password through `mobileAuth.signIn`. It looks up a persisted user, verifies the password, requires an active cooperative and membership, then issues a normal device session. The signed-in profile includes same-tenant memberships for role switching. Password login itself has no one-time-code requirement.
- The floating QA access panel asks the backend for capability. `getQaAcceleratorCapability` disables the accelerator in a production environment, and startup rejects `QA_ACCELERATOR_ENABLED=true` there. Reviewer access must use normal password sign-in, not the preview QA credential or its profile selector.
- Current source: member sign-in and the pre-entry paywall no longer depend on a tenant-plan payment; an audited tenant-plan override still cannot satisfy the personal paid-feature gate. Only a current personal store purchase or the isolated review grant can pass that gate for the signed user.
- No production reviewer account, isolated production tenant, paid entitlement, released 0.2.0 binary or end-to-end sign-in proof exists yet. A code path is not evidence that reviewers can enter the submitted app.

## Provisioning and operating procedure

1. After the eligible publisher and production backend are ready, create one clearly named *synthetic review* tenant in production. Classify it as QA data, bind a reserved `.test` source domain, and confirm it cannot be confused with a real cooperative or included in finance reporting. Do not copy live members, bank details, identity documents, receipts or transaction records. Use fictional names and harmless sample balances. Confirm the tenant is active and not being purged.
2. Create dedicated active reviewer user(s) with strong generated passwords and stable cooperative access codes. Give one reviewer both an administrator and member membership in the same tenant if the release build exposes role switching; otherwise provide separate reusable accounts. Link a synthetic member record for member screens. Do not give platform-owner or real-tenant membership. Avoid email/SMS OTP, forced password reset, location restriction and expiring access codes.
3. Superseded by the personal app access review procedure above. Do not use a tenant-plan transition to claim that an individual reviewer can enter the corrected paid mobile app.
4. Ensure all payment, payout, financing disbursement, messaging and identity-provider actions in the reviewer workspace are synthetic or safely disabled at the external boundary while screens remain inspectable. If any action could move real funds or contact a real person, stop and fix isolation before sharing access.
5. On the final signed production binary, from a clean install and an external network, sign in with the exact codes/passwords, switch roles, inspect member and admin areas, paid subscription/restore screens, financing disclosures, support/legal links and deletion entry. Sign out and repeat. Verify the personal review grant survives session renewal, backend restart and the next calendar day while unexpired; verify the unpaid account still stops at the paywall. Check that the production QA panel is unavailable and no preview backend is contacted.
6. Enter credentials **only** in Play Console's Sign-in details, with concise English navigation and role-switch instructions. Include all separate accounts needed for paid features. Keep secrets out of Git, Brain, screenshots and ordinary support messages. Maintain the account while the app remains on Play; when rotation is necessary, update console details first and retest. Monitor review-account authentication failures without logging passwords.
