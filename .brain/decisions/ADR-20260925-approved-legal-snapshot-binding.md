# ADR: Bind public policy approval to the exact published snapshot

Status: Accepted, 25 September 2026. This is a technical publication control, not legal approval of the current drafts.

## Context

Terms and Privacy acceptance records already include a version, content snapshot and SHA-256 hash. Previously, adding `published` status plus approval metadata could make edited text effective without a server-side check that the approver reviewed that exact text and metadata. The other four public pages could also show an effective label and become indexable from a status flag alone. An edit after sign-off, or a changed effective date/version, would produce a new acceptance hash but could still appear approved.

## Decision

Each `published` public policy declaration must supply `approvedSnapshotHash`. `publicPolicyApprovalHash` calculates SHA-256 over the exact serialized snapshot: document type, version, effective date, approval date, approval reference, title, introduction and sections, plus any source-owned interactive copy. The deletion page's request form, verification acknowledgement/result, unavailable notice and contact label now render from `publicDeletionFlowCopy` included in its policy snapshot. The verification email's subject, preview, body, action and event label, plus the neutral request API response, also use that source. A later edit to any of this flow copy invalidates the deletion page's approval hash. Because the policy type allows pages without interactive copy, deletion publication also requires its `interactiveCopy` to match the exact rendered flow copy; removing it and recomputing a valid hash cannot publish an unbound deletion flow. The server returns no effective Terms/Privacy document unless the configured hash equals the current snapshot hash, the version/reference are nonblank, both dates are valid and reached, and the effective date is not before approval. A missing, stale or malformed hash leaves onboarding acceptance unavailable and fail-closed. All six marketing pages use the same check for their effective label and robots metadata; a failed check keeps them non-effective and noindex. Current all-draft pages remain unchanged.

The approval reference, dates and hash must come from a real owner/legal review of the exact final source text. The hash prevents accidental post-approval changes from silently becoming effective; it does not itself prove the reviewer had authority or that the content is legally sufficient. Any legally material edit requires fresh approval metadata/hash and a new publication/deployment. All six pages are dynamically rendered so a future effective date updates both page content and robots metadata when reached, without another deployment solely for the clock transition.

Production submission preflight now requires those same six source publications to pass `isApprovedPublicPolicy` at submission time. Effective public pages expose their approved snapshot hash in a noninteractive HTML data attribute; the preflight compares each page to its source hash and compares the `/api/legal` Terms/Privacy versions and hashes to the same source. Draft or changed source, stale deployment content and mismatched acceptance documents fail the gate. A hash match is technical consistency evidence, not independent proof of reviewer authority, contact monitoring or deletion fulfilment.

## Verification

Six focused publication tests with 66 assertions cover all six page types, draft/incomplete approval, changed text, changed version/date/reference, retroactive dates, stale/duplicated acknowledgement and fresh matching approval. Domain, database and marketing TypeScript checks pass; the optimized marketing build marks all six policy pages as dynamic routes. Local HTTP checks returned 200/draft/noindex for all six and `available=false` from `/api/legal`. No live publication or acceptance was performed.
