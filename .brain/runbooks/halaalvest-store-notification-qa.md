Focused local tests pass for a personal Apple notification, a personal Play renewal, wrong-account isolation, idempotent application and withholding Google acknowledgment until an applied grant. These use injected provider evidence; there is still no real sandbox product, signed-device personal transaction, delivered Apple V2/Play RTDN, live receipt, provider acknowledgment or staffed refund reconciliation. Use `MOBILE_APP_BILLING_CATALOG` for the personal products and leave `MOBILE_APP_BILLING_SALES_ENABLED=false` until accepted. The older tenant-oriented checkpoints below are historical and do not substitute for per-user acceptance.

Equal-time conflict retry source check, 28 September: a controlled authenticated Google push now has a two-delivery test. The first entitlement application reports a same-millisecond conflict and the HTTP handler returns 503 without Play acknowledgment; the simulated redelivery re-verifies current state, applies it and acknowledges only afterward. A database fixture also confirms a one-millisecond-later fresh verification applies after the conflict. These are local injected results, not actual Pub/Sub redelivery, Play acknowledgment or provider ordering evidence. Preserve the signed license-test, delivery-attempt, dead-letter and entitlement-ledger checks below before enabling a live topic.

RTDN contract checkpoint, 28 September: the source now requires Google's documented top-level and applicable nested `1.0` versions plus an integral subscription `notificationType`. Unknown versions and incomplete subscription notices return 503 before a provider lookup or entitlement write; unfamiliar positive refund reasons are still kept for human review. The controlled HTTP fixtures now include the provider's version/type fields. A real Play test publish and monitored dead-letter path remain required. [Google RTDN reference](https://developer.android.com/google/play/billing/rtdn-reference).

Chargeback response design constraint: [Google says](https://developer.android.com/google/play/billing/provide-refund-and-chargeback-suggestions) it records the **first** `orders.reviewrefund` call and ignores later calls while returning OK. Before enabling a response mutation, require an owner-approved decision/evidence policy, authenticated operator attribution, an immutable first-call intent and exact-request retry after uncertain transport outcomes. The required API body includes the pending token, `sampleContentProvided` and `refundPreference`; do not default either factual field or send a speculative response. Test with Play's license-tester chargeback instrument, then reconcile the first submitted preference and later order outcome. Current source has no ReviewRefund caller.

Google acknowledgment gate, 28 September: the source now returns HTTP 503 and does not call Play acknowledgment when a current verified purchase still requires acknowledgment but its entitlement application reports `applied: false`. In signed license-test QA, produce or simulate a controlled unapplied event, confirm the response and no Play acknowledgment, then repair the cause and verify redelivery or Restore applies the correct entitlement before acknowledgment. Alert on this condition immediately; [Google's guidance](https://developer.android.com/google/play/billing/security) says unacknowledged purchases can be automatically refunded after three days. Do not infer the provider deadline from these mocked source tests. Existing subscription and voided-event requery checks still apply.

Platform queue checkpoint, 28 September: `/platform/refund-reviews` is a restricted read-only view of pending Google review receipts and conservative deadlines, linked from the platform privacy page. It does not expose encrypted token material or submit a recommendation. During later isolated QA, verify a signed-in platform owner can see a synthetic receipt, a tenant admin receives not-found/forbidden, an overdue item is prominent, and the paginated API never returns ciphertext or digest. The existing 503 response remains until a staffed 24-hour alert/decision/Google response path and monitored dead-letter handling are proven. Do not enable the live topic from this checkpoint alone.
Redelivery checkpoint: a new receipt records one tracked push; an exact duplicate increments the count and updates last-observed activity without replacing the first encrypted token or deadline. Verify those fields with two controlled authenticated pushes and inspect the private provider event, then compare Pub/Sub's independent delivery attempts and dead-letter backlog. Older zero-count rows display “Not tracked.” This local counter does not prove the external topic retried or that an operator was alerted.

Status: source HTTP wiring checked 28 September 2026; no live Apple or Google notification has been delivered to a HalaalVest backend. The API mounts `POST /billing/store-notifications/apple` and `/billing/store-notifications/google`. The Apple handler verifies a V2 signed payload and re-queries the current subscription. The Google handler authenticates the Pub/Sub push identity, reads the RTDN token, re-queries the Google Play Developer API, persists verified entitlement and only then acknowledges a pending purchase. Both are separate from client purchase callbacks. Source HTTP tests prove this call order with controlled provider evidence, including a 503 response and no Google acknowledgment when persistence fails. They do not prove store signatures, provider access, public routing or delivery.

## Apple V2

1. In HalaalVest App Store Connect App Information, configure distinct Production and Sandbox **App Store Server Notifications V2** URLs ending in `/billing/store-notifications/apple`. The current console fields still show **Set Up**; no saved URL is verified. Apple sends sandbox events to the Production URL if no Sandbox URL is provided, so verify both separately. [Apple URL setup](https://developer.apple.com/help/app-store-connect/configure-in-app-purchase-settings/enter-server-urls-for-app-store-server-notifications/)
2. Use Apple's **Request a Test Notification** and **Get Test Notification Status** for the Sandbox URL, then for Production only after the production endpoint is safely deployed. Record request token/status, API response and a server receipt showing that a signed `TEST` event was accepted without an entitlement grant. [Apple test guidance](https://developer.apple.com/documentation/appstoreservernotifications/enabling-app-store-server-notifications)
3. With a signed sandbox-capable iOS build and individual QA accounts, exercise purchase, restore, renewal, cancellation, expiry and refund/revocation. Compare current Apple status, HalaalVest provider event/audit and the exact buyer's personal entitlement after each transition. Retry a delivered event and verify idempotency, no cross-user grant and no cross-tenant data access. A successful test notification alone is not lifecycle acceptance.

## Google RTDN

1. After HalaalVest exists in an eligible Play Organization account, configure a Cloud Pub/Sub topic, authenticated push subscription to `/billing/store-notifications/google`, the exact OIDC audience/service email expected by the API, and Play Console **Real-time developer notifications** for subscription and voided-purchase events. Verify that the Play notifications service account can publish to the topic. [Google setup and test message](https://developer.android.com/google/play/billing/getting-ready)
   The planned Play setting includes **all voided purchases**. The source now re-verifies `productType=1` subscription voids against current Play state. `productType=2` one-time voids return non-success. A pending refund-review event records an encrypted, deduplicated provider-event receipt and still returns 503; this is safe intake, not a completed chargeback review. Configure `STORE_REFUND_REVIEW_KEYS_JSON` as a JSON object of key IDs to base64-encoded 32-byte AES keys and `STORE_REFUND_REVIEW_ACTIVE_KEY_ID` as the ID used for new receipts; retain old keys until their events are resolved and purged. Never put keys or plaintext tokens in this runbook or logs. Confirm the app has no one-time products, then establish a staffed platform-owner review queue, deadline alerting, Google `ReviewRefund` response, outcome reconciliation, retention/purge rules and monitored Pub/Sub dead-letter/backlog handling before enabling a live topic. [Google's RTDN reference](https://developer.android.com/google/play/billing/rtdn-reference) describes the 24-hour response obligation.
2. Send Play Console's test message. Record topic publish result, authenticated endpoint receipt and HTTP 200; the test message must not change a personal entitlement. Then use a Play-installed license-test build and individual QA accounts for purchase, deferred duration change/renewal, restore, cancellation, hold, expiry and refund. For each token, confirm Google API current state, exact personal catalog mapping, persisted provider event, buyer-bound entitlement and required purchase acknowledgment.
3. Exercise a controlled transient persistence failure: the handler should return 503 before acknowledgment. Restore service, observe Pub/Sub redelivery and confirm one effective entitlement transition under duplicate delivery. [Google Pub/Sub push responses](https://docs.cloud.google.com/pubsub/docs/push) state that every non-success response causes redelivery; configure and inspect retry/backoff and dead-letter handling so a poison message cannot silently starve billing reconciliation.

Keep new Production offers disabled until both store matrices, reviewed policies, public support/deletion routes, reviewer access and exact signed-binary checks pass. Store test-message success does not replace a real purchase or a delivered renewal/refund notification.
